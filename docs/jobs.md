# Background jobs (`jobs`)

Each tick runs inside a transaction holding `pg_try_advisory_xact_lock(job key)`
(`jobs::try_lock`) — one replica works, the others skip.

Spawned by `serve::run_with` after migrations; stop on the shutdown token (a run in progress finishes first).

| Job | Every | Does |
|---|---|---|
| `sweeper` | 60 s | `DELETE … WHERE expires_at < now()` on `login_transactions`, `authorization_codes`, `sessions`, `refresh_tokens`, `opaque_access_tokens`, `rate_limit_buckets`, `outbox`, `email_tokens`, `known_devices`, `webauthn_challenges`, `telegram_link_codes`, `telegram_otps`, `federation_states`, `device_authorizations` (readers already ignore expired rows; this bounds growth), and `audit_events` older than their tenant's `audit_retention_days` |
| `rotation` | 5 min | Per (tenant, alg), each tenant in its own transaction (one failing tenant doesn't block the others) while the run's lock transaction holds the leader lock: `KEY_PREPUBLISH_HOURS` before the active key is `KEY_ROTATION_DAYS` old, publish a `next` key (in JWKS, not signing); once it has been published that long, retire the active key (`expires_at` = now + the tenant's longest access-token TTL, min 1 h, + 1 h) and activate the next one — retire first, in one transaction, because the partial unique indexes allow one active key per (tenant, alg) per statement. Runs on an explicit `now` (tests move the clock) |
| `secret_expiry` | 1 h | Only with email configured, behind its own leader lock: up to 100 `client_secrets` expiring within 14 days and not yet warned (`expiry_notified_at IS NULL`) get one `secret_expiring` email per verified, enabled GlobalAdmin / ApplicationAdmin of the tenant, and `expiry_notified_at` set — in one transaction, so each secret is warned about once. Secrets of disabled tenants or tenants without such an admin are skipped and stay unmarked until someone can be warned. Explicit clock. [email.md](email.md#client-secret-expiry) |
| `outbox` | 10 s | Per channel, each only when configured: `email` (SMTP), then `telegram` (bot; chat looked up at send time, no link → dead — [telegram.md](telegram.md#notices)), and always `backchannel` (signed logout tokens POSTed to RPs — [backchannel_logout.md](backchannel_logout.md#delivery)). Claim-then-send, per channel `jobs::outbox::policy` (own leader-lock key, batch, send budget: email and telegram 8 × 60 s, backchannel 32 × 15 s): a short transaction (holding the channel's lock, so channels running side by side never make each other skip a tick) leases up to a batch of due messages of the channel (`attempts + 1`, `next_attempt_at = now + 10 min`, `SKIP LOCKED`; batch × budget + 30 s skew margin < 10 min is a compile-time check per channel), then each is sent outside any transaction (bounded by the channel's budget) — never starting a send that could end within 30 s of the lease's end, skipping a row whose lease was taken over — and recorded with its own statement fenced on the claimed `(attempts, next_attempt_at)`: sent / backoff 1 m, 5 m, 30 m, 2 h, then 6 h / dead after 8 attempts or a permanent rejection (bodies of sent and dead rows dropped, enforced by a CHECK), times taken at the outcome. Rows a run stops before (shutdown — checked between messages — or the deadline) are released (due now, attempt undone); after a crash they retry after the lease. A message past its `expires_at` is never attempted again. Each job run is its own task, so a panic is logged and the loop goes on. Logs carry id, kind and error kind only. Explicit clock. Details in [email.md](email.md#delivery) |
